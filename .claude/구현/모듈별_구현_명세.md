# 모듈별 구현 명세

> 각 모듈의 **입력/출력, 핵심 로직, 의존 관계, 주의사항**을 정리합니다.
> 구현 시 이 파일과 설계서를 나란히 펴놓고 작업합니다.

## Layer 0: 사고 접수

### IncidentCase (core/intake/incident_case.py)
- **설계서**: 5.4.2절 클래스 명세
- **DB**: incident_cases (테이블 1)
- **역할**: 사고 케이스 CRUD
- **메서드**:
  - `create()` → case_id(UUID) 생성, DB 저장
  - `updateConfig(config: JSON)` → system_config 갱신
  - `close()` → closed_at 설정
- **주의**: incident_type은 5종 enum만 허용 (`CREDENTIAL_THEFT`, `PRIVILEGE_ESCALATION`, `DATA_EXFILTRATION`, `AUDIT_LOG_TAMPERING`, `MULTI_CSP_LATERAL`)

### CollectionGuide (core/intake/collection_guide.py)
- **설계서**: 5.4.2절 + UC-01 시퀀스
- **역할**: 사고유형+CSP+구성 기반 수집 체크리스트 생성
- **메서드**:
  - `generate(type, csp, config)` → CollectionTarget 목록을 REQUIRED / CORROBORATING 분류
  - `refresh()` → 수집갭 복귀 시 체크리스트 재계산
  - `getCompletionRate()` → 필수 증거 수집 완료율 (%)
- **핵심 로직**: IncidentTypeKnowledge.lookup(type)으로 관련 ATT&CK 기법 + 핵심 서비스 조회 → collection_targets에서 해당 type+csp 필터링 → evidence_role 기준 분류
- **의존**: IncidentTypeKnowledge, CollectionTarget(DB)

### CollectionTarget (DB 모델 — 지식베이스)
- **시드 데이터 경로**: data/collection_targets/{csp}_{incident_type}.json
- **주요 필드**: target_id, incident_type, csp, log_type, evidence_role, priority(1~10)
- **주의**: 이 테이블은 지식베이스(읽기 전용), 런타임에 수정하지 않음

### IncidentTypeKnowledge (core/intake/knowledge.py)
- **역할**: 사고유형별 관련 ATT&CK 기법 + 핵심 서비스 매핑 정보 제공
- **메서드**: `lookup(incidentType)` → { relatedTechniques: [], keyServices: [] }
- **데이터 소스**: 하드코딩 또는 data/kb/ 내 JSON에서 로딩

## Layer 1: 로그 수집

### LogIngestor (core/ingestion/log_ingestor.py)
- **설계서**: 5.4.3절 + UC-02 시퀀스
- **DB**: raw_events (테이블 3)
- **메서드**:
  - `upload(file)` → multipart 파일 수신, 임시 저장
  - `verifyHash(file)` → SHA-256 해시 생성 (SNF-04 무결성)
  - `parseAndStore()` → CSP별 파서로 JSON/CSV → raw_events INSERT
  - `matchTargets()` → 각 이벤트를 collection_targets와 매칭, matched_target_id 설정
- **핵심 로직**: 파일 확장자 + 내용으로 CSP 자동 감지 → 적절한 파서 호출 → 이벤트별로 raw_events INSERT + SHA-256 저장 → collection_targets.matches(rawEvent) 호출하여 매칭
- **의존**: parsers/ncp.py, parsers/nhn.py, CollectionTarget.matches()
- **주의**: 
  - 한 파일에 여러 이벤트 포함 가능 (JSON 배열 또는 JSONL)
  - source_file 칼럼에 원본 파일명 저장
  - raw_json에 원본 전체 저장 (정규화 전 보존)

### RawEvent (DB 모델 + 도메인 객체)
- **메서드**: `toOCSF()` → OCSFNormalizer 호출하여 OCSFEvent 변환
- **주의**: raw_json은 TEXT 타입, 대용량 이벤트도 원본 보존

## Layer 2: 분석

### OCSFNormalizer (core/analysis/ocsf_normalizer.py)
- **설계서**: 5.4.4절 + 5.2.1절 필드 매핑 실증 분석
- **DB**: ocsf_events (테이블 4)
- **입력**: RawEvent (원본 JSON)
- **출력**: OCSFEvent (정규화된 이벤트)
- **핵심 로직**:
  1. rawEvent.csp로 CSP 식별
  2. data/mapping_rules/{csp}.json 로딩
  3. 필드별 매핑 적용 (eventTime→time, userName→actor.user.name 등)
  4. 누락 필드 보완 (unmapped_raw에 원본 보존)
  5. OCSF 스키마 검증 (validateSchema)
  6. ocsf_events INSERT
- **매핑 예시 (NCP Activity Tracer — 공식 가이드 기반)**:
  ```
  eventTime → time (Unix ms 정수 또는 'YYYY-MM-DD HH:MM:SS UTC' 문자열 두 형식 모두 처리)
  action → activity_name (예: Login, Access Server Console, Create access key)
  actionResultType → status_code (SUCCESS=200, FAIL=500)
  content.actionUserName → actor_user_name (콘솔/API 응답의 nested 필드)
  content.sourceIp → src_endpoint_ip (IPv4/IPv6)
  historyId, nrn, productName, regionCode, sourceType, actionUserType 등 → unmapped_raw 보존
  ```
- **매핑 예시 (NHN Cloud Trail — 공식 가이드 기반)**:
  ```
  eventTime → time (ISO8601 +0000 → DATETIME)
  eventId → activity_name (예: event_id.iam.login, event_id.iaas.s3credential.create)
  result → status_code (SUCCESS=200, FAIL=500)
  userName → actor_user_name (최상위 평탄)
  userIp → src_endpoint_ip
  userId(이메일), userIdNo(UUID), orgId, projectId, appKey, request, response 등 → unmapped_raw 보존
  ```
- **주의**: event_id FK로 raw_events와 1:1 연결 (UNIQUE 제약). NCP eventTime은 Export(ms)와 콘솔 응답(UTC 문자열) 두 형식 자동 감지 필요.

### AttackMapper (core/analysis/attack_mapper.py)
- **설계서**: 5.4.4절 + 5.2.2절 매핑 실증 분석
- **DB**: attack_events (테이블 5)
- **입력**: OCSFEvent
- **출력**: AttackEvent (또는 null — 매핑 불가 시)
- **핵심 로직**:
  1. data/attack_rules/rules.json 로딩 (startup 시 1회)
  2. 각 OCSFEvent에 대해 MappingRule 순회
  3. activityNamePattern(Regex) 매칭 + condition(JSON) 평가
  4. 매칭되는 규칙이 있으면 AttackEvent 생성 (technique_id, tactic, rule_id, risk_score)
  5. 매칭 결과 없으면 null → 해석갭 후보
- **MappingRule JSON 형식**:
  ```json
  {
    "rule_id": "R001",
    "activity_name_pattern": "ConsoleLogin",
    "condition": { "src_endpoint.ip": { "$not_in": "KR_IP_RANGES" }, "time": { "$hour_between": [0, 6] } },
    "technique_id": "T1078.004",
    "tactic": "Initial Access",
    "base_risk_score": 8.5
  }
  ```
- **주의**: 
  - ocsf_events와 0..1 관계 (매핑 안 되는 이벤트도 있음)
  - risk_score는 baseRiskScore 그대로 사용 (가중치 합산은 차후)

### GapDetector (core/analysis/gap_detector.py)
- **설계서**: 5.4.4절 + UC-04 시퀀스
- **DB**: gap_results (테이블 6)
- **입력**: caseId
- **출력**: GapResult (gapType + missing[])
- **핵심 로직**:
  1. requiredSet = collection_targets에서 evidence_role='REQUIRED'인 target_id 집합
  2. collectedSet = raw_events에서 matched_target_id가 NOT NULL인 target_id 집합
  3. mappedSet = attack_events에 매핑된 ocsf_events의 원본 raw_events target_id 집합
  4. classify():
     - requiredSet ⊆ collectedSet AND 매핑 성공 → **NONE** (갭 없음)
     - requiredSet ⊄ collectedSet → **COLLECTION** (수집갭, Layer 0 복귀)
     - collectedSet 확보했으나 매핑 실패 이벤트 존재 → **EVIDENCE** (증거갭, 수사관 판단 위임)
     - 매핑 불가 이벤트 존재 → **INTERPRETATION** (해석갭, AI 셰르파 브리핑 권장)
- **주의**: 하나의 케이스에 여러 갭 타입 공존 가능 → 가장 심각한 것 우선 반환

## Layer 3: AI 셰르파

### AISherpa (core/sherpa/ai_sherpa.py)
- **설계서**: 5.4.5절 + UC-05~07 시퀀스
- **역할**: 4가지 모드로 수사관 보조 (검색·요약·제안만, 판단하지 않음)
- **메서드**:
  - `brief(caseId, eventId)` → ATT&CK RAG 검색 → LLM 브리핑 + 출처 (SF-05)
  - `suggestMissingLink(nodeA, nodeB)` → ATT&CK × 로그 DB 교차검색 → 후보 노드 (SF-06)
  - `recommendPlaybook(chain)` → 공격 기법 기반 대응 플레이북 매칭 (SF-08)
  - `chat(caseId, sessionId, query, history)` → RAG 기반 자연어 응답 + 출처 (SF-09)
- **구현 우선순위**: brief → chat → suggest → playbook
- **핵심 원칙**: 
  - 모든 응답에 출처(source_id) 첨부
  - "AI가 판단하면 위험, 검색·요약·제안하면 안전"
  - LLM 응답 시간 > 30초 시 fallback 메시지 반환 (SNF-02)

### RAGRetriever (core/sherpa/rag_retriever.py)
- **의존**: ChromaDB
- **메서드**:
  - `retrieve(query, k)` → Vector Search로 관련 청크 k개 반환
  - `rerank(chunks)` → 관련도 기준 재정렬
- **지식베이스 4종**: ATTACK, PLAYBOOK, CSP_DOC, CASE_DB

### LLMEngine (core/sherpa/llm_engine.py)
- **의존**: Ollama (localhost:11434)
- **모델**: Llama 3.1 8B (GGUF Q4_K_M)
- **메서드**:
  - `generate(prompt)` → sLLM 텍스트 생성
  - `tokenize(text)` → 토큰화 (컨텍스트 윈도우 관리)
- **주의**: 오프라인 동작 필수, 외부 API 호출 금지

### ChatSession (core/sherpa/chat_session.py)
- **역할**: 대화 히스토리 관리 (세션별)
- **저장**: 우선 인메모리 List (DB 테이블 없음, 새로고침 시 초기화)
- **메서드**:
  - `append(msg)` → 대화 히스토리에 추가
  - `summarize()` → 세션 대화 요약 (히스토리 길어질 때)

## Layer 4: 시각화/보고

### InvestigationBoard (core/board/investigation_board.py)
- **설계서**: 5.4.6절 + UC-06 시퀀스
- **DB**: chain_nodes (테이블 7), chain_edges (테이블 8)
- **메서드**:
  - `addNode(node)` → ChainNode 추가 (수사관 수동 or AI 제안)
  - `connectEdge(fromId, toId)` → 방향성 엣지 생성
  - `finalize()` → 체인 확정 + 보고서 생성 트리거

### ChainNode
- **핵심 필드**: attackId(nullable, AI 후보는 null일 수 있음), status(CONFIRMED/REJECTED), isAiSuggested, posX, posY
- **메서드**: accept(), reject() → status 변경 + ActionLog 기록

### ReportGenerator (core/board/report_generator.py)
- **설계서**: 5.4.6절 + UC-08 시퀀스
- **의존**: Jinja2, python-docx
- **입력**: InvestigationBoard(확정된 체인) + 증거(RawEvent 목록)
- **출력**: KISA 양식 보고서 (8개 섹션)
- **섹션**: 사고 개요, 타임라인, 영향 분석, ATT&CK 결과, 대응 조치, 권고사항, 증거, 코멘트
- **메서드**:
  - `render()` → 템플릿 + 데이터 결합 → Document 객체
  - `exportDocx()` → python-docx로 .docx 파일 생성
  - `exportPdf()` → PDF 변환

## 모듈 간 의존 관계 요약

```
Layer 0 (IncidentCase, CollectionGuide)
    ↓ caseId
Layer 1 (LogIngestor → RawEvent)
    ↓ raw_events
Layer 2 (OCSFNormalizer → AttackMapper → GapDetector)
    ↓ attack_events, gap_results
Layer 3 (AISherpa ← RAGRetriever ← KnowledgeBase)  [보조 역할]
    ↓ briefing, hints
Layer 4 (InvestigationBoard → ReportGenerator)
    ↓ 보고서 (DOCX/PDF)
```

각 계층은 **아래 계층의 DB 테이블만 읽고, 자기 계층의 테이블에 쓴다**. 역방향 의존은 GapDetector → Layer 0 복귀(수집갭)만 예외.
