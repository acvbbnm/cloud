# 3축 검증 보고서 — 운영급 도달 평가

> 작성: 2026-05-17 · 기준: `dev2` 브랜치 (`3ef55ae`)
> 본 문서는 walking-skeleton·기능 동작 수준을 넘어 **운영급(현장에서 수사관이 단독으로 신뢰하고 사용할 수 있는 수준)** 도달을 위한 평가 프레임이다.
> 회의·발표·평가위원 질의·논문 작성·후속 작업 우선순위 결정의 단일 진실 출처.

## 0. 작성 배경

기존 평가는 "23 요구사항 중 몇 개 동작하는가" 의 정량 매핑(`docs/요구사항_구현_매핑.md`)에 머물렀다. 그러나 **현장 수준** 도달을 위해서는 더 깊은 3 축 평가가 필요하다.

본 보고서는 사용자가 제시한 **3 축 검증 프레임** 을 5 계층(Layer 0~4)에 적용한 15 셀 매트릭스이다.

---

## 1. 검증 프레임 (3 축)

| 축 | 평가 질문 | 기준 |
|---|---|---|
| **① 설계 정당성** | 왜 이런 시스템 구성을 넣었는가? | 외부 표준 인용 + 도메인 근거 + 학술 변호 가능성 |
| **② 유동적 대처** | 어디까지 변동·확장에 대응 가능한가? | 시드·룰·CSP·사고유형·환경 변수 추가 시 코드 수정 범위 |
| **③ 수사관 인사이트** | 실제로 인지 부하를 줄이고 가치를 주는가? | 시간 단축·못 본 관계·노이즈 감소 (정량 가능 시 측정치) |

각 셀은 다음 4 항목으로 평가:
1. **현재 상태** (구체적 사실)
2. **외부 표준·근거** (인용)
3. **정량 메트릭** (가능한 곳)
4. **운영급 갭** + 보강 추정

## 3. 계층별 상세 평가

### 3.1 Layer 0 — 사고 접수 (`core/intake/`, 875 줄)

#### ① 설계 정당성 🟢
- **현재**: V-1 위저드 (CSP → 사고유형 → 시스템 구성 → 가이드). v1 단순 시드 + v2 외부 표준 6종 기반 Kill Chain 매트릭스 병행.
- **외부 표준**:
  - **KISA 침해사고 분석절차 안내서 (제2010-8호)** §2.4 초기 대응 점검표 6항목 ↔ Step2 입력 1:1 매핑
  - **MITRE ATT&CK Cloud Matrix v14** 14 전술 (실제는 12개)
  - **Google Cloud Threat Intel** "Cloud bad log configurations" 1.x 카테고리
  - **NIST SP 800-86** §3.1 휘발성 계층 → priority
  - **ISO/IEC 27037:2012** 4단계
  - **CSA Top Threats 2024** 위협 분류
- **정량**: 9 카테고리 × 5 사고유형 × 2 CSP 매트릭스 = **90 매핑 셀** (개념적 커버리지)
- **운영급 갭**: 사고유형 5종 외 (랜섬웨어, DDoS, 웹쉘 등) 확장 시 enum + 시드 추가 — **현재는 5종 fixed**. 학기 마감 후 Phase 2.

#### ② 유동적 대처 🟢
- **새 사고유형 추가**: `models.py` enum 1줄 + `data/collection_targets_v2/categories/*.json` 9개에서 `applicable_incident_types` 배열 갱신
- **새 CSP 추가** (예: AWS): `categories/*.json` 의 `csp_mapping` 에 `aws` 키 추가만
- **새 환경 변수** (예: WAF 적용): `environment_modifiers.json` 룰 1개 추가 → 즉시 가이드 보정
- **현재 13 modifier** 가 입력값 9 종 커버
- **운영급 갭**: 시드 추가 시 검증 자동화(스키마 validator, lint) 없음. 시드 손상 시 즉시 인지 어려움

#### ③ 수사관 인사이트 🟢
- **현재**:
  - V-1 케이스 생성 5초 → 가이드 자동 표시 (기존 수사관 수동: 매뉴얼·문서 검색 30분~수시간)
  - v2 매트릭스에 출처 칩 (Google·KISA·MITRE) → "왜 이 로그 필수인가" 즉시 이해
  - 환경 보정 (MFA 미적용 → 인증 로그 우선순위 자동 +2)
- **정량** (추정):
  - 수동 분석 30분 → 시스템 사용 5초 = **약 360배 가속**
  - 가이드 우선순위 매기기 (NIST 휘발성) 자동 = 수동 매기기 5분 → 0초
- **운영급 갭**: 정량 측정치는 추정. 실제 수사관 인터뷰·사용성 평가 없음 (학기 후 후속)

### 3.2 Layer 1 — 로그 수집 (`core/ingestion/`, 455 줄)

#### ① 설계 정당성 🟢
- **현재**: NCP Cloud Activity Tracer + NHN Cloud Trail 파서 + SHA-256 해시 + collection_targets 자동 매칭
- **외부 표준**:
  - **NCP·NHN 양대 CSP** = 국내 점유율 70%+ (한국 침해사고 대응 핵심 타깃)
  - **ISO/IEC 27037:2012** 4단계 (Identification → Collection → Acquisition → Preservation) — V-2 흐름과 매핑
  - **SNF-04 로그 무결성** = SHA-256 (NIST FIPS 180-4 표준)
- **정량**: 실 raw 228건 (NCP 81 + NHN 147) + 합성 4 시나리오 (총 61건) = **289건 E2E 검증**
- **운영급 갭**: 사용자 인증·권한 X (단일 수사관 가정). 업로드 권한 제어 미구현

#### ② 유동적 대처 🟢
- **새 CSP 추가**: `core/ingestion/parsers/{csp}.py` 1 파일 + `data/mapping_rules/{csp}.json` 1 파일 + `core/ingestion/matchers.py` 분기 추가
- **새 로그 형식** (XML, syslog 등): 파서 함수 추가
- **현재 NCP·NHN 2종**. AWS·Azure·GCP 추가 시 각 1일 분량 예상
- **운영급 갭**: 실시간 스트리밍 (file watcher, kafka) 미지원 — 배치 업로드만

#### ③ 수사관 인사이트 🟢
- **현재**:
  - 업로드 시 매칭 분포 자동 표시 → "수집 가이드 5건 중 5/5 매칭" 또는 "1건 미수집"
  - 진척률 (matched/total) 가시화 → SF-04 갭 감지 입력
- **정량** (실제 검증):
  - 81건 적재 < 1초 + 매칭 100% (NCP)
  - 147건 적재 < 1초 + 매칭 4/5 = CT-NHN-IAM-002 누락 정확히 짚음
- **운영급 갭**: 1k+ 동시 업로드 미검증. 중복 차단 룰 없음 (같은 SHA-256 파일 두 번 업로드 시 raw_events 중복)

### 3.3 Layer 2 — 분석 (`core/analysis/`, 494 줄)

#### ① 설계 정당성 🟢
- **현재**: OCSF 정규화 + ATT&CK 매핑 + 갭 감지 (3 종 분류)
- **외부 표준**:
  - **OCSF 1.3 (Open Cybersecurity Schema Framework)** — Apple·AWS·Splunk 채택 표준
  - **MITRE ATT&CK Cloud Matrix v14** — 사이버보안 사실상 표준
  - **갭 분류 4종 (NONE/COLLECTION/EVIDENCE/INTERPRETATION)** = 디지털 포렌식 워크플로 모델
- **정량**: 매핑 룰 **22개 (NCP 11 + NHN 11)** — 모두 실 raw 매칭 검증
- **운영급 갭**: 룰 22 → 100+ 목표 (운영 5 사고유형 풀 커버). 사고유형 5종 중 1종(CREDENTIAL_THEFT)만 깊이 있음

#### ② 유동적 대처 🟢
- **새 ATT&CK 룰**: `data/attack_rules/rules.json` 의 `rules` 배열에 1 객체 추가 — 백엔드 자동 리로드
- **새 OCSF 필드**: `data/mapping_rules/{csp}.json` 의 `field_mappings` 1줄 추가
- **새 갭 유형**: `GapDetector.classify()` 분기 추가 (현재 4종 고정)
- **운영급 갭**: 룰 변경 후 자동 회귀 테스트 없음

#### ③ 수사관 인사이트 🟢
- **현재**:
  - V-3 좌측 raw / 우측 OCSF 양면 비교 → "어떤 필드가 어떻게 매핑됐나" 즉시 검증
  - V-4 갭 감지 → "NONE → 분석 진행 / COLLECTION → Layer 0 복귀 / EVIDENCE → 수사관 판단" 자동 안내
- **정량** (실제 검증):
  - 정규화 81건: < 1초 (NCP 100%)
  - ATT&CK 매핑 147건: < 1초 (76건 매핑)
  - 갭 감지: < 100ms
- **운영급 갭**: 정규화율·매핑 적중률·갭 정확도 자동 회귀 측정 미구현

### 3.4 Layer 3 — AI 셰르파 (`core/sherpa/`, 1124 줄)

#### ① 설계 정당성 🟢
- **현재**: Ollama gpt-oss:20b + ChromaDB + sentence-transformers + 깡통 fallback
- **외부 표준 + 설계 원칙**:
  - **CLAUDE.md / 설계서 5.1절**: "AI 는 판단·결정하지 않는다. 검색·요약·제안만"
  - **RAG (Retrieval-Augmented Generation)** = 환각 방지 + 출처 추적 가능
  - **SNF-02** 30s timeout → 규칙 fallback → 가용성 보장
  - **System prompt 6 규칙** 강제 (한국어·출처 [N] 인용·"AI 판단 X" 면책 등)
- **정량**: 4 역할 (brief·chat·suggest·playbook) × 5 엔드포인트 + 출처 칩 자동 첨부
- **운영급 갭**: AI 응답 품질 정량 평가 (BLEU, BERTScore, 수사관 만족도) 미실시. 학기 발표 시연으로는 충분

#### ② 유동적 대처 🟢
- **KB 청크 추가**: `data/kb/{attack,playbook,csp_doc,case_db}.json` 의 `chunks` 배열에 추가 → `python -m core.sherpa.embed_kb` 한 줄로 재임베딩
- **LLM 모델 교체**: `LLM_MODEL=llama3.1:8b` (또는 gpt-oss·deepseek 등) 환경변수 1줄
- **임베딩 모델 교체**: `EMBEDDING_MODEL=jhgan/ko-sroberta-multitask` 환경변수 1줄
- **외부 RAG (Pinecone, Weaviate 등)**: `rag_retriever.py` 의 `_chroma_retrieve` 함수만 교체
- **운영급 갭**: 모델 교체 시 응답 품질 변화 자동 측정 없음

#### ③ 수사관 인사이트 🟡 ← 유일한 부분
- **현재**:
  - V-8 채팅 → 출처 칩 (ATTACK·PLAYBOOK·CSP_DOC·CASE_DB 색상) → 즉시 검증
  - V-5 brief → 노드 선택 시 ATT&CK 기법 컨텍스트 5초 요약
  - 자연어 학습: "T1078.004 알려줘" → KB 인용 답변
- **정량**:
  - **KB 청크 15개** (ATTACK 3 + PLAYBOOK 2 + CSP_DOC 5 + CASE_DB 5)
  - 응답 시간: GPU 노트북 ~20초, CPU 60~120초 (gpt-oss:20b)
- **운영급 갭** 🔴: **KB 청크 15개는 시연용. 운영 50+ 필요**
  - ATTACK 3 → ATT&CK Cloud 12 전술 × 핵심 기법 = 30+ 청크
  - PLAYBOOK 2 → 사고유형 5종 × 2~3 청크 = 10+ 청크
  - CASE_DB 5 → KISA 침해사고 보고서·블로그 사례 30+ 청크
  - **추정 1~2일 보강 작업** (KISA + Google + AWS 사례 청크화)

### 3.5 Layer 4 — 보드·보고서 (`core/board/`, 542 줄)

#### ① 설계 정당성 🟢
- **현재**: InvestigationBoard (노드 + 엣지) + ReportGenerator (8 섹션) + DOCX export
- **외부 표준 + 설계 원칙**:
  - **그래프 모델 (chain_nodes + chain_edges)** = 포렌식 표준 (공격 체인은 본질적으로 그래프)
  - **3-state PENDING/CONFIRMED/REJECTED** = 사람-AI 협업 모델 (AI 제안 + 수사관 검증)
  - **KISA 침해사고 보고서 양식** ↔ 8 섹션 매핑 (overview/timeline/impact/attack_analysis/response/recommendation/evidence/comments)
  - **action_logs 이벤트 소싱** = ISO 27037 무결성 + 감사 추적
- **정량**: 4 보드 엔드포인트 + 4 보고서 엔드포인트 + SVG 그래프 시각화
- **운영급 갭**: KISA 양식과의 1:1 매핑 학술 검증 부족 (8섹션이 실제 KISA 보고서의 어느 섹션과 대응?)

#### ② 유동적 대처 🟢
- **노드·엣지 수 무제한**: chain_nodes / chain_edges 테이블 + ChainGraphCanvas 자동 격자 배치
- **보고서 섹션 추가**: `ReportGenerator.generate_draft()` 의 섹션 사전에 키 추가
- **출력 형식**: DOCX (현재) → PDF (LibreOffice headless), HTML, JSON 등 추가 가능
- **외부 BI 도구 연동**: action_logs JSON 내보내기 → Splunk·Elasticsearch 직접 import 가능
- **운영급 갭**: 보고서 템플릿이 코드에 박혀 있음. Jinja2 템플릿 외부화 권장

#### ③ 수사관 인사이트 🟢
- **현재**:
  - V-5 SVG 그래프 — 공격 체인 한눈에 (방금 UF-04 구현)
  - V-5 AI 브리핑 카드 — 노드 선택 시 ATT&CK 기법 컨텍스트 + 출처 칩
  - V-7 보고서 자동 초안 — 8 섹션 자동 채움 → 수동 작성 시간 단축
- **정량** (추정):
  - 보고서 수동 작성 2시간 → 자동 초안 + 편집 30분 = **약 4배 가속**
  - 공격 체인 시각화: 텍스트 나열 → SVG 그래프 → 회의 보고 즉시 가능
- **운영급 갭**: 보고서 정확도 (자동 초안이 실제 사고 흐름과 얼마나 일치하는가) 평가 미실시
