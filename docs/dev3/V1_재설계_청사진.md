# V-1 사고 접수 워크플로 재설계 청사진 (dev3)

> 작성일: 2026-05-18
> 대상 브랜치: `dev3` (dev2 기반 분기)
> 목표: V-1 Step 1 의 "사고유형 사용자 직접 선택" 한계 극복 — 글로벌 표준 6개 (AWS Detective, MS Sentinel, GCP SCC, TheHive, DFIR-IRIS, NIST 800-61r2) 의 "단서 누적 → 가설 형성 → 사고유형 추정" 흐름 채택

---

## 0. 배경 — 왜 재설계가 필요한가

### 현행 dev2 흐름의 한계

```
Step 0 CSP → Step 1 사고유형 5종 강제 선택 → Step 2 시스템 구성 → Step 3 가이드
```

**학술적 약점**:
- AWS·Azure·GCP·TheHive·IRIS·Velociraptor — 6개 글로벌 도구 어디서도 "사고유형 사전 선택" 강제하지 않음
- NIST SP 800-61r2 §3.2 Triage 단계는 **"scope → prioritize → categorize"** 순서. 우리는 **"categorize → scope"** 인과 역전
- 실제 IR 상황: "뭔가 이상한데 뭔지 모르는" 단계가 가장 흔함. 사고유형 모르고 시작이 자연

**실용적 약점**:
- 다중 사고유형 동반 (예: 자격증명 탈취 → 권한 상승 → 데이터 유출) 표현 불가
- 사고유형 오선택 시 가이드 자체가 잘못됨
- 사용자 입력 시점에 사고유형을 단정 → AI 셰르파의 "판단 X" 원칙과 충돌

상세 벤치마크는 `docs/벤치마크_클라우드_사고조사.md` 참조.

### 재설계 목표

1. **빈 케이스 시작** (TheHive·IRIS 모델) — 사고유형 = `UNCLASSIFIED` 기본
2. **Discovery Loop** — 단서 입력 + 부분 로그 분석 + 다음 단서 가이드 병행
3. **결정 트리 기반 사고유형 확정** — 정적 JSON, 결정성 100%
4. **AI 보조 분리** — 환각 위험 차단 (KB 검색·요약만, 결정 X)
5. **V-8 사후 검증** — Layer 2 전체 매핑 결과로 V-1 결정 보완

## 1. 사용자 결정 사항 (확정)

8 항목에 대한 사용자 답변 기록.

| # | 항목 | 결정 | 비고 |
|---|---|---|---|
| 1 | Step 1 TLP 필드 | ✅ 추가 | RED / AMBER / GREEN / WHITE |
| 2 | 부분 로그 분석 | ✅ 필수 | Step 2 진행 전 1개 이상 업로드 강제 |
| 3 | 결정 트리 질문 수 | ✅ 동적 | 단서·케이스 따라 변동, **트리 시각화 추가** |
| 4 | 임계값 | 🟡 가중치 설계 후 결정 | 학술 근거 기반 가중치 초안 후 시뮬레이션 |
| 5 | 건너뛰기 fallback | ✅ 공통 가이드 | UNCLASSIFIED → Phase 0 공통 카테고리 |
| 6 | V-8 사후 검증 | ✅ 유지 | Layer 2 전체 매핑 vs Step 2 확정 사고유형 정합성 |
| 7 | 결정 트리 진입 사전 안내 | ✅ 추가 | 단서 종류별 모달 가이드 |
| 8 | DB 설계 | ✅ 위임 | 본 청사진 §5 참조 |

추가 결정:
- **사고유형 enum**: 현 5종 (`CREDENTIAL_THEFT`, `PRIVILEGE_ESCALATION`, `DATA_EXFILTRATION`, `AUDIT_LOG_TAMPERING`, `MULTI_CSP_LATERAL`) + `UNCLASSIFIED` 추가
- **MULTI_CSP_LATERAL**: 보존 (삭제 후 시퀀스 패턴으로 표현하자는 안 보류)
- **시각화 라이브러리**: react-flow (V-7 Board 와 동일)

#### Discovery Loop 의 3개 활동

| 활동 | 입력 | 출력 | 학술 근거 |
|---|---|---|---|
| **① 단서 입력** | IP/계정/해시/도메인/시각/서비스명 (6종) | observable 객체 | DFIR-IRIS IOC + NIST 800-61r2 표 3-2 + Velociraptor artifact |

## 6. API 변경

### 6.1 신규 엔드포인트

```
POST /api/triage/analyze
  입력: { caseId, clue: {type, value}, partial_log_file? }
  처리:
    1) log_ingestor.partial_ingest(partial_log_file)       # Layer 1 호출
    2) ocsf_normalizer.normalize(ingested_events)          # Layer 2 호출
    3) attack_mapper.map(ocsf_events)                       # Layer 2 호출
    4) triage_engine.update_hypothesis(case_id, clue, mapped)
    5) next_clue_planner.suggest(case_id, current_clues)
  응답: {
    mapped_events: [...],
    hypothesis_scores: { CRED: 45, PRIV: 25, ... },
    next_clues: [...],
    kb_results: { case_db: [...], attack: [...], playbook: [...] }
  }

POST /api/triage/next
  입력: { caseId, current_node_id, answer_id }
  처리:
    1) triage_engine.apply_weights(case_id, node, answer)
    2) decision_tree.next_node(node, answer)
  응답: {
    next_node: { question, options },
    hypothesis_scores: { ... },
    tree_path: [...],            # 시각화용
    is_terminal: false
  }

POST /api/triage/confirm
  입력: { caseId, incident_type, secondary_incident_types? }
  처리: case_id 의 incident_type 확정, action_log 기록
  응답: { case }

GET /api/triage/tree?caseId=
  결정 트리 시각화용 — 현재까지 진행 경로 + 가능 경로
  응답: { nodes: [...], edges: [...], current_node, completed_path }
```
