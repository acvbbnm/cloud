## 0. 가중치 설계 원칙

### 원칙 1: 학술 근거 필수
모든 가중치는 **출처 1개 이상**과 함께 정의. 캡스톤 평가에서 "임의 결정" 비판 차단.

### 원칙 2: 단위는 5
점수 단위는 5/10/15/20/25/30/35/40 만 사용. 학술 변호 시 "임의 미세 조정 아님" 입증.

### 원칙 3: 단일 임계값 도달 가능성
1개 답변/단서/기법이 단독으로 임계값(70) 을 넘기지 않음. 최대 단일 점수 = 40.
→ 사고유형 확정은 항상 **2개 이상의 시그널 누적** 필요.

### 원칙 4: 사고유형 9종에 대한 점수 매트릭스 (dev3 C-1 확장, 2026-05-19)
```
CREDENTIAL_THEFT      (CRED)   PRIVILEGE_ESCALATION  (PRIV)
DATA_EXFILTRATION     (DATA)   AUDIT_LOG_TAMPERING   (AUDIT)
MULTI_CSP_LATERAL     (MULTI)  RANSOMWARE            (RANS)   🆕
MISCONFIG_EXPOSURE    (MISC)   🆕
PHISH_INITIAL_ACCESS  (PHISH)  🆕
INSIDER_THREAT        (INSIDER) 🆕
```
이전 표(`5종 CRED/PRIV/DATA/AUDIT/MULTI`)는 호환을 위해 모든 항목에 9종 키 보존.
신규 4종은 학술 근거 있는 항목만 명시 점수, 그 외는 0 기본값.

### 원칙 5: 출처 인용 표준
- **MITRE**: `MITRE ATT&CK v14 — T[ID]`
- **KISA**: `KISA 침해사고 분석절차 안내서 §[조항]`
- **NIST**: `NIST SP 800-61r2 §[조항] 표 [번호]`
- **Google**: `Google Cloud Threat Intel §[조항]`
- **CSA**: `CSA Top Threats to Cloud Computing 2024 — #[번호]`
- **ISO**: `ISO/IEC 27035-1:2023 §[조항]`

## 5. 임계값 산정 — 시뮬레이션

### 시나리오 1: 전형적 CREDENTIAL_THEFT

```
입력:
- Q1: csp_alert         → CRED +15
- Q2A: 비정상 로그인     → CRED +25
- Q2A: 비국내 IP         → CRED +20
- 단서: 비국내 IP       → CRED +25
- 부분 분석: T1078.004   → CRED +25
- env: MFA 미적용 (m-004) → CRED +25

합산: CRED = 135  ← 임계값 70 크게 초과
```

→ **자동 확정 (≥90 + 2위 격차 ≥30)** 트리거 가능

### 시나리오 2: 복합 사고 (CRED + PRIV)

```
입력:
- Q1: csp_alert         → CRED +15, PRIV +10
- Q2A: 비정상 로그인     → CRED +25
- Q2A: 권한 변경         → PRIV +30
- 단서: 권한 변경 계정  → PRIV +35
- 부분 분석: T1078.004   → CRED +25
- 부분 분석: T1098       → PRIV +30
- env: MFA 미적용        → CRED +25

합산: CRED = 90, PRIV = 105

격차 < 20 → 복합 사고유형 제시
```

→ **메인 PRIV + 부 CRED** 제시

### 시나리오 3: 약한 시그널 (임계값 미달)

| `high_confidence` | **70** | 시나리오 1,4,5 모두 70 크게 초과. 시나리오 3 (약한 시그널) 은 미달로 추가 질문 진행 |
| `auto_skip_tree` | **90** | 단일 사고유형 90+ 시 결정 트리 자동 건너뜀 (시나리오 1,4,5) |
| `gap_to_2nd` | **20** | 1·2위 격차 ≥20 면 단일, 미만이면 복합 제시 (시나리오 2 = 복합) |
| `terminal_score` | **120** | 단일 사고유형 120+ 시 즉시 종합 판정 제시 |

## 7. 가중치 갱신 절차

1. 새 ATT&CK 기법 추가 시 → §3 표에 추가, weights.json 에 매핑 등록
2. 새 결정 트리 질문 추가 시 → §1 에 학술 근거 + 가중치 부착
3. 시뮬레이션 시나리오 추가 시 → §5 에 추가, 임계값 재검증
4. 가중치 단위 5 위반 시 → 거부 (테스트 케이스 추가 권장)

## 8. 학술 변호 — 캡스톤 평가 대비 Q&A

**Q: 왜 결정 트리의 가중치가 5/10/15/20/25/30/35/40 단위인가?**
A: 임의 미세 조정을 차단하기 위해 의도적으로 거친 단위로 설계. 학술 평가 시 "가중치 정밀도 = 학술 근거 정밀도" 비율 유지.

**Q: T1078.004 가 CRED +25 인 이유는?**
A: MITRE ATT&CK Cloud Matrix v14 의 Tactic 분류 — TA0006 Credential Access 직접 매핑. 단독으로 임계값 70 도달 못 함 → 추가 시그널 강제.

**Q: m-001 (auditEnabled 비활성) 이 AUDIT +30 인 이유는?**
A: 감사 로그 비활성 환경은 KISA §2.4 의 점검표 ⑥ "네트워크 연결 지점 기록 불가" 상태. AUDIT_LOG_TAMPERING 의 직접 증거이며, 다른 사고유형의 시그널 은닉 가능성 시사. NIST SP 800-86 §3 휘발성 계층에서 가장 우선 휘발성으로 분류.

**Q: 멀티 CSP 시그널 (동일 IP NCP+NHN) 가 MULTI +35 인 이유는?**
A: 실 raw 데이터 분석에서 IP 115.91.214.5 가 NCP·NHN 양쪽 환경에 등장한 사례 기반. CSA Top Threats 2024 #11 APT 와 결합. 단독으로 임계값 미달이지만, multi_cloud=있음 (m-010 +30) 과 함께 누적되면 65 → 추가 시그널 1개로 70 도달.

**Q: 가중치 매트릭스의 결정성은 어떻게 보장되는가?**
A: 정적 JSON 파일 1개로 저장. 같은 입력 → 같은 점수 → 같은 사고유형 추정. 캡스톤 재현성 평가 통과.
