## 논의 흐름 요약

### 1단계 — 벤치마킹 (조사)

**사용자 요청**: "해외 CSP 환경의 사고조사 워크플로우 (특히 AWS) 를 벤치마킹하고 우리 프로그램과 비교"

**조사 결과** (병렬 3개 agent):
- AWS GuardDuty + Detective + Security Hub + Incident Manager
- Microsoft Sentinel + Defender for Cloud + Defender XDR
- Google SCC + SecOps + Mandiant
- TheHive 5 + DFIR-IRIS + Velociraptor
- NIST SP 800-61r2 + SANS PICERL + ISO/IEC 27035-1 + MITRE D3FEND

**공통 결론**:
> 글로벌 표준 8개 모두 "사고유형을 사용자에게 처음 묻지 않는다."
> 룰/매핑이 사고유형을 결정하고 분석가는 검증한다.

### 2단계 — V-1 재설계 방향 결정

| 옵션 | 사용자 결정 |
|---|---|
| 1-A: TheHive·IRIS 모델 (빈 케이스) | ✅ 채택 (기본 골격) |
| 1-B: 결정 트리 + UNCLASSIFIED 병행 | ✅ 결합 |
| 1-C: Detective Profile Guidance | (1-A+1-B 에 포함) |

**사용자 의도**:
> "빈 케이스에서 시작 + 사고유형 확정 단계에서 결정 트리 사용.
> AI 는 환각 위험이 있으니 결정 자체는 트리 + 사용자가 하고
> AI 는 케이스 관련 정보·과거 사례·예시를 가져오는 역할만"

### 3단계 — 결정 트리 위치 수정

**사용자 지적**:
> "결정 트리는 V-1 내부 (Step 2 직후) 에 위치해야지 V-8 으로 미루면 안 됨"

**수정**:
- V-1 Step 2: 시스템 구성 → Discovery Loop (단서 + 분석 + 트리)
- V-1 Step 3: 사고유형 확정 후 정밀 가이드
- V-8: 사후 검증 (Layer 2 전체 매핑 vs 확정 사고유형 정합성)

### 4단계 — Step 2 Discovery Loop 구체화

**사용자 의도**:
> "단서 입력과 로그 분석, 다음 단서를 찾을 가이드가 이 단계에서 병행하면서
> 사고유형 확정에 도움이 되는 방안으로.
> 사고유형이 확정된 후로는 어느정도 흐름이 명확하니까"

**Discovery Loop 3개 활동** 확정:
1. 단서 입력 (IP·계정·해시·도메인·시각·서비스명)
2. 부분 로그 분석 (단서 시각 ±5분)
3. 다음 단서 가이드 (단서 → 다음 단서 그래프)

### 5단계 — 8 항목 세부 결정

| # | 항목 | 사용자 답변 | 청사진 반영 |
|---|---|---|---|
| 1 | Step 1 TLP 필드 | ✅ 추가 | `tlp` 칼럼, RED/AMBER/GREEN/WHITE |
| 2 | 부분 로그 분석 | ✅ 필수 | Step 2 진행 강제 |

| 4 | 임계값 | 가중치 설계 후 결정 | 학술 근거 부착 후 시뮬레이션 |

| 8 | DB 설계 | 위임 | 본 청사진 §5 |

### 6단계 — dev3 분기 작업 착수 결정

**사용자 결정**:
> "변경사항이 너무 많이 생길거같으니 dev3 에 현재까지 진행사항은 dev2 에 기록되어있으니
> dev3 에서 새롭게 시작.
> dev2 를 복사해서 dev3 만들고 지금까지 논의했던 변경점과 구조를 dev3 에 기록"

## 핵심 설계 원칙 (재설계 전반 관통)

### 원칙 1: 결정성 100%
- 결정 트리 = 정적 JSON
- 가중치 = 정적 JSON
- 같은 입력 → 같은 결과
- 캡스톤 재현성 평가 통과

### 원칙 2: AI 역할 분리
- AI 가 결정하지 않음 — 결정은 트리 + 사용자
- AI 는 KB 검색·요약·과거 사례·예시·플레이북 추천만
- 환각 위험 차단 — 원본 출처 URL 함께 표시

### 원칙 3: 사고유형 후행 분류
- TheHive·IRIS·NIST·AWS·Azure·GCP — 6개 표준 공통
- Step 1: UNCLASSIFIED 시작
- Step 2: 결정 트리로 좁히기
- V-8: Layer 2 매핑으로 검증·보완

### 원칙 4: 다중 사고유형 지원
- 단일 사고유형 가정 한계 해소
- 메인 사고유형 + 부 사고유형 분리 (DB `secondary_incident_types`)
- AWS AttackSequence + Defender XDR attack story 패턴

### 원칙 5: 오프라인 폐쇄망 호환
- 외부 CDN·API 호출 X
- 모든 데이터·룰·KB 정적 JSON
- LLM 도 로컬 Ollama gpt-oss:20b
