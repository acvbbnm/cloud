# 벤치마크 — 클라우드 사고조사 도구·방법론

> 작성일 2026-05-18 · 대상 시스템: AI Sherpa (dev2)
> 목적: V-1 Step 1의 "사용자 직접 사고유형 선택" 한계를 극복하기 위한, "단서 누적 → 가설 형성 → 사고유형 추정" 방식 설계의 외부 근거 수집

---

## 1. Executive Summary (요약 5~7줄)

1. **가장 유사한 도구는 AWS Detective** — 그래프 기반 entity-finding 피벗으로 "엔티티 한 개에서 시작해 꼬리에 꼬리를 무는" 우리가 지향하는 UX를 이미 구현했고, **사고유형을 처음부터 묻지 않는다**. (시작점: GuardDuty Finding 또는 IP/User 직접 검색)
2. **모든 상용 도구는 "사고유형 사전 선택"을 하지 않는다.** 모두 "알람 클릭" 또는 "엔티티 검색"으로 시작하며, 사고유형 분류는 **조사 결과로** 산출된다 (MITRE ATT&CK Tactic 사후 매핑).
3. **dev2의 V-1 Step 1은 업계 흐름과 정반대**다. 학술적·실용적 변호력 모두 약함. 단, 폐쇄망·국내 CSP·한글 RAG·외부 표준 6종 인용은 **고유 강점**으로 유지 가능.
4. **차용 가치 Top 1**: Sentinel의 **Exploration Query (Entity hover → "이 IP와 연결된 알람은?")** 패턴. 결정 트리보다 자유도가 높고 구현 난이도 중.
5. **차용 가치 Top 2**: Detective의 **finding overview → entity profile → pivot** 3단계 워크플로우. 우리의 V-2~V-5에 그대로 매핑 가능.
6. **다음 작업 우선순위**: (a) V-1 Step 1을 "단서 입력 화면"으로 재설계 (CSP·증상 키워드·의심 IP/계정 입력) + (b) 결정 트리 노드 5종(=incident_type) 설계 + (c) 매핑룰 JSON에 "단서→사고유형 추정 가중치" 컬럼 추가.

## 2. 도구별 상세 분석

### 2.1 AWS Detective (가장 유사)

| 항목 | 내용 |
|---|---|
| 분류 | AWS Native / Graph-based Investigation |
| 시작점 | (a) GuardDuty Finding 클릭 → "Investigate in Detective" 피벗 (b) Security Hub Finding (c) IP/User/Role 직접 검색 |
| 진행 방식 | **3-phase**: Triage(true/false positive 판정) → Scoping(범위·시간·관여 entity 확장) → Response. Entity profile 시각화 → 연관 entity로 pivot → 시간축에서 baseline 대비 이상 행위 탐색 |
| 시스템 구성 입력 | **자동** (CloudTrail · VPC Flow Logs · GuardDuty · EKS audit 자동 ingest, AWS Config 통합) |
| 사고유형 분류 시점 | **사후** — finding group이 ATT&CK Tactic으로 자동 라벨링 |
| 강점 | 1주~수개월 baseline 자동 학습, "Finding Group"으로 다중 finding 자동 묶음, AWS 데이터 zero-config |
| 약점 | AWS 단일 CSP, 한국 CSP 미지원, 폐쇄망 미지원, 한글 X |
| dev2 시사점 | **finding overview → entity profile → pivot 3단계를 그대로 차용** (V-2 로그 → V-5 보드 → V-6 ATT&CK 매트릭스 흐름과 매칭). "처음에 사고유형 묻지 않음"의 결정적 선례 |
| URL | https://docs.aws.amazon.com/detective/latest/userguide/detective-investigation-about.html |

## 6. 결정 트리 트리아주 설계 권고

### 6.1 어떤 도구가 가장 좋은 모델인가?

**Sentinel Exploration Query > Decision Tree**. 이유:
- Sentinel은 명시적 트리가 아닌 **"entity별 다음 질문 추천"** 방식 — 가지치기보다 자유 탐색이 자연스럽다
- Decision Tree는 학술 변호엔 좋지만 사용자 UX엔 경직됨
- **타협안**: 백엔드는 결정 트리(가중치 매핑룰 JSON), 프론트는 Exploration Query UX

### 6.2 결정 트리 노드 수·깊이 권장

```
Depth 1 (CSP 선택)         : naver / nhn / all                    → 3
Depth 2 (1차 단서 카테고리) : 인증·권한·데이터·로그·네트워크         → 5
Depth 3 (구체 증상)        : 카테고리당 평균 4개                   → 20
Depth 4 (추정 사고유형)    : 5종 enum 가중치 (확률 표시)            → 5
```

총 노드 ≈ **3 + 5 + 20 + 5 = 33개**, 깊이 **4단계**. 사용자는 평균 **2~3 클릭**으로 후보 사고유형 도달.

### 6.3 사고유형 enum 구성 — 변경 없이 유지 권고

기존 5종(CREDENTIAL_THEFT, PRIVILEGE_ESCALATION, DATA_EXFILTRATION, AUDIT_LOG_TAMPERING, MULTI_CSP_LATERAL)을 그대로 **추정 결과의 enum**으로 사용. 변경 없이도 결정 트리 결과로 매핑 가능.

**핵심**: V-1 Step 1의 화면 문구만 변경
- 현재: "사고유형을 선택하세요"
- 목표: "발견한 단서를 입력하세요" + 백엔드가 가중치로 추정 → "추정 사고유형: CREDENTIAL_THEFT (78%), PRIVILEGE_ESCALATION (15%) ..." 표시
