## 4. 다이어그램 읽는 법

본 설계서에는 **5종 다이어그램**이 등장합니다. 각각 보는 법이 다릅니다.

### 4.1 UML Class Diagram (Ⅵ-1)

| 표기 | 의미 |
|---|---|
| `□ ClassName` 윗칸(색상) | 클래스 이름 |
| `- field : Type` 가운데칸 | 속성 (private 가정) |
| `+ method() : Return` 아랫칸 | 메서드 |
| `─→ 1..*` | "1 대 다" 관계 (한 IncidentCase에 여러 RawEvent) |
| `┄→ 0..1` | 점선 = 약한 의존, 0..1 = 있을 수도 있음 |
| `creates / feeds / reads sets` | 라벨이 곧 관계 의미 |

**색상 구분**:
- 🟧 주황 = Layer 0 (사고 접수)
- 🟦 청록 = Layer 1 (수집)
- 🟦 파랑 = Layer 2 (분석)
- 🟪 보라 = Layer 3 (AI)
- 🟩 초록 = Layer 4 (보드/보고서)
- 🟨 노랑 = Common

> **2장 분할 이유**: 한 그림에 모두 넣으면 박스가 작아져 글자가 안 보이므로, **Part 1 = 데이터 파이프라인(Layer 0/1/2)**, **Part 2 = AI·UI·공통(Layer 3/4 + Common)**로 나눴습니다.

### 4.2 UML Sequence Diagram (Ⅵ-2)

8개 그림(UC-01~08), 시간은 **위 → 아래**로 흐릅니다.

| 표기 | 의미 |
|---|---|
| 상단 가로 박스 | **참여자(Lifeline)** — 객체 또는 액터 |
| 점선 세로축 | 참여자의 생존 시간 |
| 실선 화살표 → | **동기 호출** (메서드 호출) |
| 점선 화살표 ⇢ | **반환값** |
| 자기 자신 → | **self-call** (내부 처리) |
| 노란색 배경 박스 | **alt** — 분기/대안 시나리오 (예: UC-04의 NONE/COLLECTION/EVIDENCE) |

**읽는 순서 예시 (UC-01)**:
```
1) User → SetupView : selectCSP()           ← 사용자가 CSP 선택
2) SetupView → IncidentCase : create(csp)   ← 케이스 생성
... (반복)
4) [다음] 클릭 → generate(...) 가이드 생성
   → KnowledgeBase 조회 → checklist 반환
   → 사용자 화면에 체크리스트 표시
```

### 4.3 DFD (Data Flow Diagram, Ⅵ-3)

| 표기 | 의미 |
|---|---|
| ◯ 원 | **프로세스 (P1~P8)** — 데이터를 변환하는 작업 |
| ▭ 반열린 박스 | **데이터 저장소 (D1~D9)** — DB 테이블 또는 파일 |
| ▢ 직사각형 | **외부 엔티티** — 수사관, CSP 로그, 지식베이스 |
| → 실선 | **주 흐름** (데이터 이동) |
| ⇢ 점선 | **DB 읽기/쓰기** |

**3가지 핵심 흐름**:
1. **정상 흐름** (검정): P1 → P2 → P3 → P4 → P5 → P7 → P8
2. **수집갭 복귀** (빨강): P5 → 외부엔티티(수사관) → P1 (가이드 갱신 후 재투입)
3. **증거갭 위임** (주황): P5 → 수사관 (AI 분석 한계 알림)

### 4.4 ERD (Ⅵ-5-1)

| 표기 | 의미 |
|---|---|
| 박스 윗칸 | 테이블명 |
| `PK` (빨강) | Primary Key |
| `FK` (파랑) | Foreign Key |
| `IDX` (회색) | 인덱스 컬럼 |
| `?` 접미사 | Nullable |
| `1:N`, `0..1` 라벨 | 관계 카디널리티 |

**테이블 9개를 3개 그룹으로 묶어 보세요**:
- **사고/수집**: incident_cases, collection_targets
- **이벤트 파이프라인**: raw_events → ocsf_events → attack_events / gap_results
- **수사 결과**: chain_nodes, chain_edges, action_logs

### 4.5 화면 흐름도 (Ⅶ-2)

| 표기 | 의미 |
|---|---|
| 색상 박스 V-1~V-8 | 8개 View 화면 |
| 파랑 화살표 (Happy Path) | 정상 진행 순서 |
| 빨강 화살표 | 갭 발생 시 V-1으로 되돌아감 |
| 보라 화살표 (FAB) | 모든 뷰에서 AI 셰르파 챗봇 호출 |
| 회색 화살표 | 직접 이동 (V-7로 점프) |

## 5. 추적성 (어떤 게 어떤 거랑 연결되나)

설계서 곳곳의 항목들은 **다음과 같이 1:1로 연결**됩니다. 한 줄을 따라가면 요구사항부터 구현까지 모두 추적됩니다.

```
요구사항 (SF/UF)
    ↓
Use Case (UC-01~08)             ← Ⅵ-2 시퀀스 다이어그램
    ↓
참여 클래스 (SetupView, IncidentCase 등)  ← Ⅵ-1 클래스 다이어그램
    ↓
DB 테이블 (incident_cases 등)    ← Ⅵ-5 ERD
    ↓
REST API 엔드포인트              ← Ⅵ-7 API 명세
    ↓
화면 View (V-1)                  ← Ⅶ-1 화면 정의서
```

**예시 — "사고 접수" 추적**:
| 항목 | 위치 |
|---|---|
| 요구사항 SF-00, UF-00, UF-01 | Ⅲ장 |
| UC-01 시나리오 | Ⅵ-2.1 |
| 참여 클래스: SetupView, IncidentCase, CollectionGuide, KnowledgeBase | Ⅵ-1.2 (Layer 0) |
| DB: incident_cases, collection_targets | Ⅵ-5.2 |
| API: `POST /api/cases`, `GET /api/cases/{id}/guide` | Ⅵ-7.1 |
| 화면: V-1 (4단계 위저드) | Ⅶ-1.1 |

**Ⅵ-6 요구분석 매트릭스**에 이 추적표가 한꺼번에 정리되어 있으니 거기를 펼치면 빠릅니다.

## 8. 잘못 읽기 쉬운 포인트 (주의사항)

1. **Class Diagram이 2장으로 분할**된 이유 — 별개 시스템이 아니라 **하나의 통합 구조**를 가독성 위해 나눈 것입니다. 두 그림을 같이 봐야 전체 구조가 보입니다.

2. **Sequence Diagram의 점선 화살표**는 "선택적 호출"이 아니라 **반환값**을 의미합니다 (UML 표준).

3. **DFD의 Process 번호 (P1~P8)** — Layer 번호와 1:1 대응이 아닙니다. (예: Layer 2 분석에 P3·P4·P5 세 개)

4. **갭(Gap) 3종**:
   - **NONE**: 갭 없음 → 정상 진행
   - **COLLECTION**: 수집 가이드 미충족 → Layer 0 복귀해 더 수집
   - **EVIDENCE**: 수집은 됐지만 매핑 안됨 → "AI도 모르는 기법일 수 있음" → 수사관 판단

5. **AI 셰르파 호출은 자동 아님** — 사용자가 노드 클릭 / FAB 클릭으로 **명시 호출** 시에만 동작합니다.

6. **`AI셰르파_설계서_v2.docx`(원본)에는 다이어그램이 없습니다.** 그림이 임베드된 최종본은 **`AI셰르파_설계서_v2_완성.docx`**입니다.
