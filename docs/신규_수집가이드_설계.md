# AI Sherpa — 신규 수집 가이드 설계서 (v2)

> 브랜치: `dev2` · 작성: 2026-05-15 · 담당: 김병우 (sasumm25-lab)
> 비교 대상: `dev` 브랜치의 "기존 구조 + 근거 보강" 버전 (다른 팀원 진행)

---

## 0. 작성 배경

기존(`dev`) 시스템의 가이드 생성 로직은 다음과 같은 한계가 있다:

1. **`CollectionGuide.generate()`가 `incident_type` + `csp` 두 필드만 사용** — 시스템 환경 입력(`vpc_id`, `services`, `auditEnabled` 등)이 가이드 생성에 영향 없음
2. **`collection_targets` 시드 5건의 분류 근거 부재** — 사고유형별 임의 분류
3. **외부 표준 인용 없음** — KISA/MITRE/NIST/Google Cloud 표준과의 매핑 명시 X
4. **사고유형 5종이 MITRE 14 전술 중 임의 선정** — 학술 변호 어려움

기존 구조에 사후 근거만 다는 접근(`dev` 브랜치 작업)은 학술 변호력이 약하다. **외부 표준을 청사진으로 채택한 뒤 우리 시스템을 그 위에 재설계**하는 게 정도(正道)이며, 본 문서는 그 재설계안을 명시한다.

## 1. 채택 표준 (사전 합의)

본 v2 시스템은 다음 6개 외부 표준을 **사전 채택**한 위에 설계된다.

| 표준 | 본 시스템 활용 |
|---|---|
| **KISA 침해사고 분석절차 안내서** (제2010-8호) | 7단계 절차 / 초기 대응 점검표 6항목 / 데이터 분류 (호스트·네트워크·기타) |
| **MITRE ATT&CK Cloud Matrix** (v14) | 14 전술 / 기법 ID / 매핑 룰 출처 |
| **NIST SP 800-86** (Forensic Techniques) | 휘발성 계층 / 4단계 포렌식 절차 / Evidence Hierarchy |
| **ISO/IEC 27037:2012** | 디지털 증거 처리 4단계 (Identification → Collection → Acquisition → Preservation) |
| **Google Cloud Threat Intel** — Cloud Log Configurations | 9 로그 카테고리 / 9 침해 단계 매트릭스 |
| **CSA Top Threats to Cloud Computing 2024** | 위협 카테고리 11종 / 보조 매핑 |

## 2. 핵심 설계 원칙 (기존 구조 대비 변경점)

| 영역 | 기존 (`dev`) | 신규 (`dev2`) |
|---|---|---|
| 분류 체계 | 사고유형 5종 → 시드 5건 (임의 분류) | **Google 9 카테고리 × MITRE Kill Chain × CSP 매트릭스** |
| 가이드 생성 입력 | `incident_type` + `csp` 만 | + **`system_config`의 모든 필드 동적 반영** |
| 시드 단위 | 사고유형별 5건 | **카테고리별 1건 × N 사고유형 매핑** |
| 우선순위 | 임의 부여 | **NIST/KISA 휘발성 계층 명시** |
| 가이드 UI | 단순 체크리스트 | **Kill Chain 단계 매트릭스** + 단계별 필수 로그 그룹화 |
| 출처 표시 | 없음 | 각 항목에 KISA / MITRE / Google / NIST 인용 칩 |
| API | `GET /api/guide?caseId=` | **`GET /api/guide/v2?caseId=` 신규 (기존 유지)** |

핵심: **기존 `/api/guide` 엔드포인트는 그대로 유지**. v2는 병행 동작. 사용자가 V1 Step3에서 토글로 두 버전 비교 가능하도록 설계.

## 4. 새 가이드 생성 로직 — `CollectionGuideV2`

```python
class CollectionGuideV2:
    """v2 가이드 생성기 — 표준 기반 매트릭스 + system_config 동적 반영."""

    @classmethod
    def generate(cls, db: Session, case_id: str) -> Optional[dict]:
        case = db.get(IncidentCaseModel, case_id)
        if case is None:
            return None

        # 1단계: 사고유형 → Kill Chain 단계 매핑
        phases = cls._lookup_phases(case.incident_type)  # incident_type_phases.json

        # 2단계: 각 Phase에 매칭되는 카테고리 시드 수집
        categories = cls._categories_for_phases(phases, case.csp)

        # 3단계: system_config 환경 변수 반영 (priority 부스팅 / 추가 항목)
        categories = cls._apply_environment_modifiers(categories, case.system_config)

        # 4단계: NIST/KISA 휘발성 우선순위 정렬
        categories = sorted(categories, key=lambda c: c["volatility_priority"], reverse=True)

        # 5단계: Kill Chain 단계별 그룹화
        grouped = cls._group_by_phase(categories)

        return {
            "caseId": case_id,
            "completionRate": cls._compute_completion_rate(db, case_id, categories),
            "phases": grouped,
            "applied_modifiers": cls._modifiers_log(case.system_config),
            "source_standards": [
                "Google Cloud Threat Intel — Cloud Log Configurations",
                "MITRE ATT&CK Cloud Matrix v14",
                "KISA 침해사고 분석절차 안내서 (제2010-8호)",
                "NIST SP 800-86 §3.1 (휘발성 계층)"
            ]
        }
```

## 9. 다른 팀원 작업과의 충돌 회피

`dev` 브랜치에서 진행되는 "기존 구조 + 근거 보강" 작업과 **파일 충돌 없음**:

| 파일 | dev 작업 | dev2 작업 |
|---|---|---|
| `backend/data/collection_targets/*.json` | rationale 메타 추가 | 손대지 않음 (별도 v2 디렉토리) |
| `backend/data/attack_rules/rules.json` | rationale 메타 추가 | 손대지 않음 |
| `backend/core/intake/collection_guide.py` | 변경 없음 | 손대지 않음 |
| `backend/api/intake.py` | 변경 없음 | **추가만** — v2 엔드포인트 |
| `frontend/.../Step3_GuideChecklist.tsx` | 출처 칩 추가 | 손대지 않음 |
| 신규 디렉토리/파일 | — | `collection_targets_v2/`, `Step3_GuideChecklist_V2.tsx` |
| 신규 문서 | `docs/근거_매핑.md` | `docs/신규_수집가이드_설계.md` |

**머지 순서 (사용자 결정)**:
1. 두 PR 모두 완성 후 **비교 매트릭스 작성**
2. 시연 데이터로 두 버전 동작 비교
3. 학술 변호력 / 시연 임팩트 / 개발 비용 기준 채택 결정
4. 단일 채택 or 하이브리드 (v2 매트릭스 + v1 rationale 메타 둘 다)
