## 0. 인수인계 컨텍스트 — 왜 dev2가 필요한가

### 발견된 핵심 약점 (`dev` 브랜치 기준)
1. `CollectionGuide.generate()`가 `incident_type` + `csp` 두 필드만 사용
2. V1 Step2의 시스템 환경 입력 7개 필드(`vpc_id`, `services`, `auditEnabled` 등)가 **DB에 저장만 되고 가이드 생성에 영향 X**
3. `collection_targets` 시드 5건 분류 근거 부재 — 우리(2026-05-12)가 raw log 보고 임의 분류
4. 사고유형 5종(`CREDENTIAL_THEFT` 등)이 MITRE 14 전술 중 임의 선정 — 학술 변호 부재
5. `IncidentTypeKnowledge`는 5종 사고유형 dict 정의했지만 **dead code** (호출처 없음)

### 진단 결과
- **사후 근거 추가**(=`dev` 트랙)는 변호력 약함 — "동작은 하지만 왜 그렇게 만들었나" 답이 빈약
- **외부 표준 사전 채택 → 시스템 재설계**(=`dev2` 트랙)가 정도(正道) — "이 시스템은 표준 6종에 기반"이라고 강하게 변호 가능
- 두 트랙 PR 모두 완성 후 비교·결정. dev2는 그 중 하나의 답안.

## 5. NIST SP 800-86 — 휘발성 계층

**URL**: https://nvlpubs.nist.gov/nistpubs/legacy/sp/nistspecialpublication800-86.pdf

> PDF binary 직접 추출 불가. 일반 알려진 내용으로 정리.

### 5.1 휘발성 우선순위 (Volatility Order)

```
1. CPU 레지스터/캐시        ← 가장 휘발성 높음 (즉시 소멸)
2. RAM (메모리)
3. 네트워크 연결 상태
4. 임시 파일 시스템
5. 디스크 데이터            ← 가장 휘발성 낮음 (장기 보존)
```

### 5.2 우리 priority 1~10 부여 기준 (NIST + KISA 결합)

| priority | 의미 | 예시 |
|---|---|---|
| **10** | 즉시 휘발 + 사고 시각 확정 핵심 | 인증 로그 (1.5.1) |
| **9** | 휘발 + 권한 변경 단서 | 권한 변경 (1.5.2) |
| **8** | 휘발 + 측면 이동 단서 | 서버 콘솔 접근 |
| **7** | 안정 보존 + 사고 영향 단서 | API 액세스 |
| **5** | 보강 증거 (안정 보존) | Object Storage 다운로드 |
| **3** | 부수 활동 | 리소스 변경 |

→ NIST SP 800-86 §3.1 + KISA 안내서 §2.6 결합 정당화.

### 5.3 포렌식 4단계 (NIST + ISO 27037 결합)

```
1. Collection / Identification — 잠재 증거 식별 + 수집 시작
2. Examination / Acquisition — 데이터 추출 + 무결성 (SHA-256 등)
3. Analysis — 사고 시나리오 재구성
4. Reporting / Preservation — 보고서 + 장기 보존
```

→ 우리 시스템의 L1 (수집) → L2 (분석) → L4 (보고)와 1:1 매핑.

## 6. ISO/IEC 27037:2012 — 디지털 증거 처리 4단계

### 6.1 4단계 (각 단계의 우리 시스템 대응)

| 단계 | 의미 | 우리 시스템 매핑 |
|---|---|---|
| **Identification** | 잠재 증거 식별 | V1 가이드가 "어떤 로그를 봐야 하는가" 알려줌 |
| **Collection** | 적절한 방법으로 수집 | V2 드롭존 + multipart 업로드 |
| **Acquisition** | 무결성 보장 획득 | LogIngestor의 **SHA-256 검증** |
| **Preservation** | 원본 보존 | `raw_events.raw_json` (TEXT) 영구 저장 |

### 6.2 우리 시스템에 적용할 라벨링

V2 업로드 시 화면 단계 표시:
```
① Identification (잠재 증거 식별)     ← 사용자 파일 선택
② Collection (수집)                  ← multipart 업로드
③ Acquisition (획득) ✓ SHA-256        ← 해시 검증 후 raw_events 적재
④ Preservation (보존) ✓               ← DB 영구 저장 + action_logs
```

→ V2 UI에 4단계 progress bar 표시. 수사관이 ISO 27037 어느 단계 진행 중인지 인지.

→ **본질적 차이**: CSA는 방어자 관점(미스컨피그·가시성), MITRE/우리는 공격자 관점(단계). 우리는 MITRE 가까운 분류이므로 "본 시스템은 MITRE 기반 단계 분류 채택" 명시 필요.

## 8. 6개 표준 공통 안내 패턴 (dev2 채택)

표준들이 **공통적으로** 채택하는 안내 원칙:

1. **절차 흐름 명시** — "입력 → 식별 → 수집 → 분석 → 보고" (KISA·NIST·ISO 공통)
2. **단계별 체크리스트** — 사고 유형마다 "이것을 확인하라" (KISA·Google)
3. **공격 단계 × 필요 로그 매트릭스** — Kill Chain 단계마다 필수 로그 (Google·MITRE)
4. **휘발성 우선순위** — 빨리 사라지는 데이터부터 (KISA·NIST)
5. **증거 무결성 명시** — 해시·체인 오브 커스터디 (ISO 27037·NIST)
6. **표준 분류 채택 명시** — 자체 분류가 아닌 외부 표준 인용 (CSA·MITRE)

→ **dev2 신규 가이드의 안내 모델**:
```
Phase 1. 사고 분류 (KISA 점검표 6항목)
   ↓
Phase 2. Kill Chain 단계 가설 (MITRE 14 전술)
   ↓
Phase 3. 단계별 필수 로그 안내 (Google 9 카테고리 매트릭스)
   ↓
Phase 4. 휘발성 우선순위 (KISA·NIST)
   ↓
Phase 5. 증거 수집·무결성 (ISO 27037 4단계)
   ↓
Phase 6. 분석·매핑 (OCSF + ATT&CK + 갭)
   ↓
Phase 7. 보고 (KISA 양식)
```

## 11. 결론 — 왜 표준 채택이 필요한가

**기존(dev) 시스템의 약점**:
> "왜 5종이냐?", "왜 이 7개 입력 필드냐?", "왜 IAM-001이 P10이냐?" — 현재 답이 없음.

**dev2 표준 채택 후 변호 가능성**:
> "본 시스템은 KISA(제2010-8호) + MITRE ATT&CK Cloud v14 + NIST SP 800-86 + ISO/IEC 27037:2012 + Google Cloud Threat Intel + CSA Top Threats 2024 — 6종 외부 표준을 사전 채택하여 설계됨"

이 한 문장으로 캡스톤 학술 평가의 가장 큰 약점(근거 부재)이 해소됨. 다른 계정에서 dev2 작업을 이어받아 완성하면 학술적·실무적 가치 동시 확보 가능.

작업 시작 시 추가 질문 있으면 PROGRESS.md의 "현재 진행 상황" 섹션 참조.
