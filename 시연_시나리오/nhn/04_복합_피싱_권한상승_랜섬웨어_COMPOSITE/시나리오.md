# 시연 시나리오 — NHN 복합사고 (PHISH_INITIAL_ACCESS → PRIVILEGE_ESCALATION → RANSOMWARE)

> **CSP**: NHN Cloud · **사고유형(복합)**: PHISH_INITIAL_ACCESS + PRIVILEGE_ESCALATION + RANSOMWARE · **심각도**: critical
> **공격자 외부 IP**: 94.156.169.42 (A·B 진입), 185.220.101.7 (C 운영) · **피해 계정**: finance@corp.kr → 백도어 Owner backup-svc@corp.kr
> **설계 목표**: ① 복합 사고유형 ② A→B→C 체인 재구성 ③ B→C→A 역추적("꼬리에 꼬리") ④ 쓰레기 로그 혼입 후 분류 입증

## 0. 이 시나리오가 기존 단일 시나리오와 다른 점

샘플 로그(`01_사고유형선정_nhn_composite.json`)에는 **공격 16건 + 쓰레기(`_noise`) 6건 = 22건**이 시간순으로 섞여 있다.

## 1. 사고 개요 (수사관 관점)

운영 서비스가 오후에 중단되고 Object Storage 파일이 `.locked` 로 바뀐 채 랜섬 노트가 발견됐다. 암호화를 수행한 계정 `backup-svc@corp.kr` 는 **사고 당일 Owner 권한을 새로 받은 계정**이었다. 수사관은 "이 권한을 누가 줬나"를 거슬러, 피싱 → 권한 상승 → 랜섬의 **3단 복합 사고**임을 확인한다.

## 2. 1단계 — 사고유형 선정용 로그 업로드 (쓰레기 포함)

- **파일**: `01_사고유형선정_nhn_composite.json` (공격 16 + 쓰레기 6 = 22건)
- **쓰레기 로그 6건** (모두 미매핑되어야 정상):
  `console.dashboard.load` · `billing.invoice.view` · `iaas.instance.metric.get` · `dns.zone.list` · `notification.email.send` · `cdn.cache.purge`
- **시스템 판정**: 매핑된 공격 기법이 세 묶음으로 군집 →
  - **A 묶음** T1110(Brute Force)·T1556(Modify Auth/MFA)·T1078.004 → **PHISH_INITIAL_ACCESS**

- 수사관은 **복합(RANSOMWARE 주(主) + PHISH·PRIVILEGE_ESCALATION 종(從))** 으로 확정.

## 6. 역추적 — B→C→A "꼬리에 꼬리를 무는" 재구성

```
                       ┌──────────── (B→A 역추적) ────────────┐
                       │  "backup-svc 에게 Owner 를 누가 줬나?" │
                       │  grant_owner 의 주체                   │
                       ▼  = finance / 94.156.169.42            │
        ┌──────────────────────┐                               │
   A ◀──┤ 94.156.169.42 (외부IP)├── 이 IP 의 과거 이력 조회 ───▶ 13:30 Login FAIL ×2 + MFA disable (A 발견)
        └──────────────────────┘
                       ▲
                       │  (B 시작점) org.iam.role.grant_owner → backup-svc  ★
                       │
                       ▼  (B→C 정추적) "backup-svc 는 뭘 했나?"
        ┌──────────────────────┐
   C ◀──┤ backup-svc (계정)     ├── 이 계정의 행위 추적 ──────▶ 14:10 .locked 업로드 / 14:15 볼륨삭제 (C 발견)
        └──────────────────────┘
                       │
                       ▼  (C→A 루프 폐합) vpc.delete_end 의 IP = 94.156.169.42
                          → A 의 피싱 진입 IP 와 동일 → 단일 행위자 확정 ◎
```

- **피벗 키 1 — 계정 `backup-svc`**: B(권한 부여)와 C(랜섬 실행)를 잇는다.
- **피벗 키 2 — IP `94.156.169.42`**: A(피싱)와 C(최종 VPC 삭제)를 잇는다. 공격자가 마지막에 첫 IP를 재사용 → **C에서 A로 직접 점프**.
- **피벗 키 3 — 계정 `finance`**: A(피싱 피해 계정)와 B(권한 부여 주체)를 잇는다.
- 세 피벗이 삼각형으로 닫혀 **A·B·C 어느 노드에서 출발해도 나머지 둘을 복원**.

## 7. 수사 결론

- **확정 사고유형**: 복합 — PHISH_INITIAL_ACCESS(진입) → PRIVILEGE_ESCALATION(Owner 탈취) → RANSOMWARE(암호화·파괴), 단일 행위자.
- **노이즈 처리**: 쓰레기 6종(샘플) + 1종(수집물)은 전부 `unmapped_raw` 로 분리 → 공격 신호만 체인 진입. **분류 입증 완료.**
- **갭(GapDetector)**: 없음 — 세 피벗 키(backup-svc, 94.156.169.42, finance)로 인과 완결.
- **참고(매핑 주의)**: `object.upload` 는 룰 우선순위상 T1567(Exfiltration)로 매핑될 수 있음 — 이중협박 랜섬에서 사전 유출과 암호화가 동일 API로 기록되는 현실 반영. Impact 확정은 볼륨/VPC 삭제(T1490·T1485)로 보강.
- **후속 권고**: 94.156.169.42·185.220.101.7 차단, finance 자격증명 회수·MFA 재강제, backup-svc Owner 권한 즉시 회수·계정 삭제, users.csv 4.2GB 유출 통지, **오프사이트 백업 부재**(볼륨·VPC 삭제로 복구 불가)가 근본 원인.
